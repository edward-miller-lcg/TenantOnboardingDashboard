# Architecture

## System Overview

```
Facility Browser
    │  URL: /onboarding/{guid-token}  (no login required)
    ▼
Angular 21 App — nginx (port 4200 / 80)
    │  /api/* → proxy_pass to onboarding-service
    ▼
ASP.NET Core 10 OnboardingService (port 5100)
    │  Persists onboarding session state → SQL Server
    │  Proxies business calls to link-cloud microservices
    ├──► Tenant Service         :8074  (create facility record)
    ├──► DataAcquisition        :8065  (FHIR connection test, POI)
    ├──► Report Service         :8072  (generate/list test reports)
    └──► Normalization Service  :8068  (CRUD normalizations)
```

## Onboarding Session Model

Each facility receives a unique URL containing a GUID token. The token maps to an `OnboardingSession` record that tracks:
- Facility identity (NHSN Org ID, Health System Name)
- Selected EHR vendor (Epic or Cerner — drives conditional UI)
- Step completion status (which of the 11+ wizard steps are done)
- Form data (FHIR URL, Patient List IDs, encounter type maps, etc.)

The token guard on every wizard route validates the token against the database on first load and loads the session into Angular's `SessionService` (signal-based state).

## Key Design Decisions

**No login for MVP** — Facility users access via a unique URL generated by a Link admin. The URL token is validated on every request.

**BFF pattern** — The Angular app talks only to the `onboarding-service`. All link-cloud service calls are proxied through it, keeping the frontend decoupled from link-cloud's internal API surface.

**Vendor-conditional UI** — EHR vendor (Epic vs Cerner) is captured on Server Info and stored in the session. Authorization and Patients of Interest pages render different forms based on this.

**`readEnvironmentVariable()` for secrets** — Bicep `.bicepparam` files use this function to read `SQL_ADMIN_PASSWORD` from the process environment at deploy time, so no secrets are ever committed.

**nginx `envsubst`** — The Angular app's nginx config is a template. `API_URL` is injected at container start, making the same Docker image work for both local Docker (container name) and Azure (Container App FQDN).

## Data Flow — Connection Test

1. User enters Patient FHIR ID on the Connection Test page
2. Angular POSTs to `/api/onboarding/{token}/connection-test`
3. `OnboardingService` looks up the stored FHIR base URL from session form data
4. Makes a GET to `{fhirBaseUrl}/metadata` (FHIR CapabilityStatement)
5. Returns `{ success: true/false, errorDetails?: string }` — always HTTP 200
6. Angular updates the UI based on the `success` field
